# Производительность дашборда

Изменения не затрагивают реализацию анализа цен конкурентов. Его пространства `parser*` и `competitor*` исключены из общего бюджета производных ответов.

## Память и диагностика

`GET /api/admin/performance` доступен после штатной авторизации дашборда или с серверным CRON bearer. Ответ содержит revision, RSS/heap/external, event-loop lag, очередь тяжёлых расчётов и оценочный объём кешей. Ключи кешей, тела заказов, контакты покупателей и секреты не выдаются.

`DASHBOARD_RESULT_CACHE_MB` задаёт бюджет управляемых производных результатов; по умолчанию 96 МиБ. Это оценка размера объектов, не жёсткий предел RSS всего процесса: исходные ERP-данные, live-каталог, индексы и память runtime существуют отдельно. Общий LRU учитывает пространства кеша; одиночный результат более 16 МиБ не удерживается, просроченные значения удаляются раз в 30 секунд. Для компактного готового набора поиска допускается запись до 64 МиБ внутри того же общего бюджета; повторяющиеся месячные ячейки используют общие неизменяемые объекты. Одинаковые одновременные загрузки объединяются. Карточки, поиск и диагностики используют очередь максимум двух независимых тяжёлых расчётов. Вложенные чтения источников не должны повторно захватывать эту очередь.

BigQuery использует тот же бюджет RAM и прежний дисковый кеш. Компактные производные отчёты сохраняются через `dashboard-report-cache`: срок в памяти не продлевает возраст результата с диска, на пространство сохраняется не больше 64 файлов, старые файлы удаляются при записи. Существующие ERP бинарные кеши этот механизм не удаляет.

## Помесячные отчёты

`/api/sales/monthly` возвращает один компактный ответ за 1–12 месяцев, включая сравнение. ERP рассчитывается за один обход исходных документов. Сохраняются прежние правила дат создания/полной отгрузки, исключения услуг, распределения возвратов, каналов и сегментов. Поступления получают два непрерывных диапазона из общего Orders-кеша, группируют по месяцу Киева, исключают будущие дни последнего месяца. Позиции товаров для таблицы не строятся.

Индексы категорий, брендов, менеджеров и возвратов переиспользуются по объекту исходного ERP-снимка. После замены снимка строятся новые индексы, старый массив не удерживается WeakMap.

## Кошики

Upstream `/carts/` не применяет проверенные параметры date_from/date_to. История синхронизируется на диск по 200 записей с параллельностью не более двух страниц; полная история не собирается в массив Node.js. Доступны истории больше прежних 100 страниц. Защитный потолок дисковой синхронизации — 10 000 страниц; это не лимит массива RAM.

В `DASHBOARD_CACHE_DIR/carts/<scope>/` публикуется manifest только после завершения всех страниц. Первый запрос без снимка ждёт синхронизацию; далее последний успешный снимок выдаётся сразу, устаревший обновляется фоном. Принудительное обновление ожидается, но при сбое сохраняется последний полный снимок. Ответ содержит `fetched_at` и `stale`.

Период и ID кошика применяются при постраничном чтении снимка: в памяти остаётся выбранный период или один кошик. Существующие расчёты интерфейса по выбранному периоду сохранены; серверная пагинация/агрегация этого интерфейса остаётся отдельным этапом при росте самих выбранных периодов. Старые поколения имеют двухминутный grace-период для читателей и удаляются при следующей успешной синхронизации. Файлы содержат персональные данные и создаются с закрытыми правами 0600/0700.

## Карточки, поиск и диагностики

Lite-снимок хранится в `DASHBOARD_CACHE_DIR/products-lite.json.gz`; production fallback — `/var/cache/agromat-analytics`. Он переживает замену `.next`, используется асинхронно, одновременные холодные чтения объединяются. Повторяющиеся дескрипторы атрибутов используют общие объекты при неизменном содержимом. Ответы карточек кешируются на 15 минут с ключом версии каталога; мутации очищают результат, прогресс синхронизации читается отдельно.

Готовая поисковая аналитика кешируется по дню, версии каталога, Sheet revision и состоянию обработок/исключений, без отдельной пересборки на каждую страницу. Веб-агрегаты продаж дополнительно учитывают версию ERP. Снимки акций читаются асинхронно, история метаданных обрабатывается последовательно. CPO повторно читает сохранённую диагностику по версии исходного куба и алгоритма (`diagnostics/v2`); BigQuery audit — готовый отчёт по подписи исходного файла.

## Сборка и публикация

Workflow `Build production release` запускается вручную на выбранной Git-ревизии в GitHub Actions: Node 24, npm ci, тесты, Next build, Linux standalone архив. В архив не включаются `.env*`; runtime-секреты остаются на VPS.

1. Закоммитить только изменения задачи и отправить revision в GitHub.
2. Запустить workflow на этой revision, дождаться успешных тестов/сборки.
3. Скачать `production-release`, передать `release.tar.gz` на VPS.
4. Запустить штатный `scripts/deploy.sh` с `RELEASE_ARCHIVE=/absolute/path/release.tar.gz` и нужными APP_DIR/PM2_NAME.
5. Скрипт проверяет, что встроенная REVISION совпадает с fetched origin/main до очистки сборки. Затем устанавливает standalone, копирует runtime env/static/public и перезапускает PM2 без npm ci/build на VPS.
6. Проверить HTTP, revision и функции. Удалять старые артефакты только после успешной проверки.

Без RELEASE_ARCHIVE прежний сценарий серверной сборки сохранён. В рабочем процессе revision выставляется из Git, а не из устаревшего значения `.env`.

Прогрев проверяет готовность приложения до запросов. Существующие lock и ограничение параллельности сохранены. Изменений Redis eviction или удаления постоянных пользовательских записей в коде нет: лимиты инфраструктуры рассчитываются по фактическому повторному замеру.

## Возврат временной памяти ОС

На Linux RSS может расти при относительно стабильном heap из-за фрагментации glibc: это отдельно описано в [документации Node.js](https://nodejs.org/docs/latest-v24.x/api/process.html#processmemoryusage). По этому признаку нельзя объявлять утечку JavaScript.

Штатный deploy задаёт только для процесса дашборда `MALLOC_ARENA_MAX=2`, `MALLOC_TRIM_THRESHOLD_=131072`, `MALLOC_MMAP_THRESHOLD_=131072`, если они явно не переопределены. Фиксированный mmap-порог делает крупные временные буферы возвращаемыми ОС после освобождения; arena/trim ограничивают удержание небольших выделений. Значения и семантика описаны в [документации GNU libc](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html). Redis и соседние сервисы не перенастраиваются. Эффект и задержки следует сравнивать на одном сценарии после рестарта, включая холодное чтение снимков, а не по одному значению RSS сразу после запуска.

On Linux, deployment prefers an already installed jemalloc library if LD_PRELOAD is not explicitly set. This applies only to the dashboard child process; no packages are installed and no other services are reconfigured. The settings `dirty_decay_ms:1000,muzzy_decay_ms:0,narenas:2` bound arena count and unused-page retention; background_thread remains disabled. See the [jemalloc manual](https://jemalloc.net/jemalloc.3.html). Set `DASHBOARD_NODE_ALLOCATOR=system` to disable preload, or `JEMALLOC_LIBRARY` for a different library path/architecture. Diagnostics report the selected mode; RSS must still be verified after the same workload.
